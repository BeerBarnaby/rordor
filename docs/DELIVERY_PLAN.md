## 0. เป้าหมายจริงของการส่งมอบ

> **นศท. เปิดเว็บแล้วฝึกจนจบได้เองภายใน 5 นาที และครูเห็นผลว่าฝึกแล้วได้อะไร โดยไม่ต้องพึ่งผู้พัฒนา**

แค่ส่งไฟล์ให้ครบไม่ได้แปลว่าสำเร็จ ต้องผ่านครบ 3 ข้อนี้ถึงจะนับว่าส่งมอบสำเร็จ

1. **คุณค่าต่อผู้เรียน (Value):** มีหลักฐานจาก นศท. จริงว่าฝึกจบได้และเข้าใจลำดับการช่วยเหลือมากขึ้น
2. **ความเป็นเจ้าของ (Ownership):** ครูใช้หลังบ้านได้เอง และรู้ว่าระบบล่มต้องติดต่อใคร
3. **ความยั่งยืน (Sustainability):** คนที่มารับช่วงต่อสร้างระบบใหม่ได้จากเอกสารใน repo

## 2. หลักการวางแผน

1. **ไม่เพิ่มฟีเจอร์ก่อนมีผู้ใช้จริง** ระบบครบตามขอบเขตแล้ว คอขวดคือการพิสูจน์ ไม่ใช่การสร้างเพิ่ม
2. **วัดผลโดยไม่แก้โค้ด** ช่วงทดลองให้ผู้เข้าร่วมสร้างโปรไฟล์ (แก้ G2 ได้ทันที) ส่วนการวัดความรู้ใช้ Google Form ก่อน–หลัง
3. **ความปลอดภัยต้องมาก่อนเปิดให้ผู้ใช้จริง** ต้องแก้ G3 ก่อนมีข้อมูลของคนอื่นในระบบ
4. **ทุก phase ต้องจบด้วยสิ่งที่มีคนได้ใช้จริง** ไม่ใช่จบที่ "เอกสารเสร็จ"

## 3. Roadmap

```text
พ.ย.                ธ.ค.                                     ม.ค.–ก.พ. 2570
26 27 28 ─ 4        5 ─────────── 18      21 ── 25          ────────────►
[P0 Secure]        [P2 Pilot + แก้ไข]     [P3 Handover]     [P4 Support]
    [P1 Pilot-ready]
    ├─ M1: ปลอดภัย พร้อมเปิดให้คนอื่น (27 พ.ย.)
    ├─ M2: ชุดทดลองพร้อม + ผ่านทดสอบมือถือจริง (4 ธ.ค.)
    ├─ M3: นศท. ≥ 20 คนฝึกจบ + มีข้อมูลประเมิน (18 ธ.ค.)
    ├─ M4: ลงนามส่งมอบ ครูใช้หลังบ้านได้เอง (25 ธ.ค.)
    └─ M5: จบระยะสนับสนุน ปิดโครงการ (28 ก.พ. 2570)
```

**งานที่ทำคู่ขนานได้:** ส่งเนื้อหาให้ผู้ตรวจ (P1) ระหว่างทำ P0 · แก้รูปเล่มส่วนที่ไม่เกี่ยวกับผลทดลอง (P3) ระหว่างรอคาบทดลอง (P2)
**งานที่ต้องเรียงลำดับ:** P0 → เปิดให้ผู้ใช้จริง · P2 → เขียนผลทดลองในรูปเล่ม · P3 โอนสิทธิ์ผู้ดูแล → หมุน secret

> วันที่ทั้งหมดเป็น**สมมติฐาน** ขึ้นกับตารางฝึกของหน่วย ถ้าเลื่อน ให้เลื่อนทั้งแผน แต่ห้ามข้าม Gate

## 7. Technical debt (ไม่ขวางการส่งมอบ แต่ต้องบันทึก)

1. ฟังก์ชัน v1 ที่ยังเปิดให้ anon (G9) → เลิกใช้ในโค้ดก่อน แล้วเขียน migration ปิดสิทธิ์ (ทำหลัง P2 เพื่อไม่ให้เปลี่ยนระบบระหว่างทดลอง)
2. ตาราง v1 ที่ผูกกับ Supabase Auth (`mission_attempts` ฯลฯ) ซึ่งว่างและไม่ได้ใช้
3. ประวัติ migration ใน Dashboard ไม่ครบ ให้ใช้ไฟล์ใน repo เป็นหลัก
4. ไม่มี OTP / ลืม PIN ด้วยตัวเอง
5. ไม่มีการวัดผลโหมด Guest (ถ้าต้องการ ให้เพิ่ม analytics แบบไม่ระบุตัวตนในรุ่นถัดไป)
6. ยังไม่มีนโยบายระยะเวลาเก็บข้อมูล

## 8. หลังส่งมอบ: สิ่งที่ควรพัฒนาต่อ (เรียงตามคุณค่า)

1. ระบบลืม PIN ที่ไม่ต้องพึ่งครู
2. ส่งออกผลเป็น CSV ให้ครูใช้ประกอบการประเมิน
3. สถานการณ์จำลองเพิ่ม (ใน DB รองรับ `SCENARIO_ROTC_BUILDING`, `SCENARIO_ROTC_ACTIVITY` อยู่แล้ว)
4. Analytics โหมด Guest แบบไม่ระบุตัวตน
5. ใช้กับหน่วยฝึกอื่นได้ (แยกหน่วยใน `school_name` / เพิ่มฟิลด์หน่วยฝึก)
