# รายงานหลักการทำงานของระบบน้องพร้อม

วันที่จัดทำ: 17 ตุลาคม 2569  
ระบบที่ตรวจสอบ: <https://rordor37.vercel.app>  
ขอบเขต: หน้าเรียน ภารกิจฝึก ระบบสมาชิก คะแนน แบบประเมิน หลังบ้าน API ฐานข้อมูล และการรักษาความปลอดภัย

## 1. บทสรุปผู้บริหาร

“น้องพร้อม” เป็นเว็บแอปสำหรับทบทวนการช่วยเหลือผู้หมดสติ โดยออกแบบให้ผู้เรียนเริ่มใช้งานได้ทันทีโดยไม่บังคับเข้าสู่ระบบ เส้นทางหลักประกอบด้วยการประเมินเหตุ การฝึกแจ้งเหตุ 1669 และการฝึกจังหวะ CPR ส่วนการใช้ AED เป็นบทเรียนเสริม ผู้เรียนที่ต้องการบันทึกผลข้ามอุปกรณ์ รับ XP ส่งแบบประเมิน หรือแสดงชื่อในอันดับผู้ฝึก จึงค่อยสร้างโปรไฟล์ด้วยเบอร์โทรและ PIN

ระบบแบ่งความรับผิดชอบเป็นสามชั้น ได้แก่ หน้าเว็บสำหรับการเรียนและโต้ตอบ เซิร์ฟเวอร์ Next.js สำหรับตรวจคำขอและจัดการเซสชัน และ Supabase สำหรับเก็บข้อมูลพร้อมบังคับกฎด้านสิทธิ์และความถูกต้องอีกชั้นหนึ่ง วิธีนี้ช่วยให้เบราว์เซอร์ไม่ต้องถือรหัสลับของฐานข้อมูลหรือ token เซสชันโดยตรง

ระบบเหมาะสำหรับใช้เป็นสื่อฝึกและทดลองใช้แบบมีผู้ดูแล แต่คะแนนจากหน้าเว็บยังไม่ควรถูกใช้เป็นผลสอบ การรับรองทักษะ หรือการประเมินภาคปฏิบัติ

## 2. วัตถุประสงค์ของระบบ

1. ทำให้ผู้เรียนเข้าใจลำดับการช่วยเหลือเมื่อพบผู้หมดสติ
2. ฝึกเลือกข้อมูลที่ควรแจ้งต่อศูนย์ฉุกเฉิน 1669
3. ฝึกจังหวะการกดหน้าอกให้อยู่ในช่วงเป้าหมาย 100–120 ครั้งต่อนาที
4. ให้ผู้เรียนเห็นผล จุดที่ควรทบทวน และกลับมาฝึกซ้ำได้
5. ให้ครูฝึกหรือผู้ดูแลเห็นภาพรวมการใช้งานโดยไม่เปิดข้อมูลให้บุคคลทั่วไป
6. เก็บความคิดเห็นหลังใช้งานเพื่อนำไปปรับบทเรียนและประสบการณ์ใช้งาน

## 3. หลักการออกแบบการใช้งาน

### 3.1 เริ่มฝึกได้โดยไม่บังคับเข้าสู่ระบบ

ผู้ใช้แบบ Guest สามารถเปิดบทเรียนและทำภารกิจหลักได้ทันที เพื่อลดอุปสรรคก่อนเริ่มเรียน การเข้าสู่ระบบมีไว้สำหรับความสามารถที่ต้องผูกกับบุคคล เช่น ประวัติผล XP อันดับ และแบบประเมิน

### 3.2 เรียนก่อน ฝึกต่อ และสรุปผลทันที

ระบบใช้วงจรการเรียนรู้ดังนี้:

```text
เลือกบทเรียนหรือภารกิจ
        ↓
อ่านและดูตัวอย่างสำคัญ
        ↓
ประเมินเหตุและเรียงลำดับ
        ↓
จำลองการโทรแจ้ง 1669
        ↓
ฝึกจังหวะ CPR
        ↓
ดูผลและหัวข้อที่ควรทบทวน
        ↓
บันทึกผล/XP เมื่อเข้าสู่ระบบ
```

### 3.3 ลดภาระทางความคิดระหว่างสถานการณ์ฉุกเฉิน

หน้าฝึกแสดงการกระทำปัจจุบันเป็นสิ่งเด่นที่สุด ลดข้อความที่ไม่จำเป็น และใช้คำสั่งตรงไปตรงมา เช่น “เริ่มฝึก” “เลือกคำตอบ” และ “แตะ” สีแดงใช้กับการกระทำสำคัญหรือสถานะฉุกเฉิน ไม่ใช้เป็นเพียงของตกแต่ง

### 3.4 คะแนนเป็นแรงจูงใจ ไม่ใช่การรับรอง

XP และอันดับผู้ฝึกช่วยกระตุ้นให้กลับมาฝึกซ้ำ แต่ไม่สามารถยืนยันความลึกของการกด ตำแหน่งมือ การคืนตัวของหน้าอก คุณภาพการช่วยหายใจ หรือความสามารถภาคปฏิบัติได้

## 4. สถาปัตยกรรมและองค์ประกอบ

```text
ผู้ใช้บนมือถือ/แท็บเล็ต/คอมพิวเตอร์
              │
              ▼
หน้าเว็บ React และ Next.js
  • บทเรียนและภารกิจ
  • ความคืบหน้าชั่วคราวในเครื่อง
  • โปรไฟล์และหลังบ้าน
              │ HTTPS
              ▼
Next.js API บน Vercel
  • ตรวจชนิดและขนาดข้อมูล
  • ตรวจคำขอว่ามาจากเว็บเดียวกัน
  • อ่าน/เขียนคุกกี้เซสชัน
  • ตรวจสิทธิ์ผู้ดูแล
              │ RPC
              ▼
Supabase PostgreSQL
  • โปรไฟล์และเซสชัน
  • ผลการฝึกและแบบประเมิน
  • กฎจำกัดการส่งข้อมูล
  • ข้อมูลและ audit log ของหลังบ้าน
```

| ส่วนประกอบ | หน้าที่ |
|---|---|
| React Client | แสดงเนื้อหา รับการแตะ คำนวณสถานะการฝึก และแสดงผลตอบกลับ |
| Next.js Route Handlers | เป็นประตูกลางระหว่างหน้าเว็บกับฐานข้อมูล ตรวจข้อมูลและจัดการคุกกี้ |
| Vercel | Build และให้บริการหน้าเว็บ/API ผ่าน HTTPS |
| Supabase | เก็บข้อมูลถาวร ตรวจสิทธิ์ และบังคับข้อจำกัดระดับฐานข้อมูล |
| Local Storage | เก็บความคืบหน้าชั่วคราวและคิวรอส่ง ไม่เก็บ bearer token |

## 5. หลักการทำงานของผู้ใช้ทั่วไป

### 5.1 Guest

1. เปิดหน้าเว็บและเลือกบทเรียนหรือเริ่มภารกิจ
2. ระบบเก็บสถานะที่จำเป็นในเบราว์เซอร์
3. ผู้ใช้ทำภารกิจหลักและดูผลได้
4. หากยังไม่เข้าสู่ระบบ ผลจะไม่ถูกผูกกับโปรไฟล์ส่วนกลางและไม่สามารถส่งแบบประเมินได้

### 5.2 การสร้างโปรไฟล์

ผู้ใช้กรอกชื่อที่แสดง เบอร์โทร PIN โรงเรียน และชั้นปี/สถานะ เบอร์โทรจะถูกปรับให้อยู่ในรูปแบบเดียวกันก่อนตรวจซ้ำ PIN ถูก hash ในฐานข้อมูลและไม่เก็บเป็นข้อความปกติ

### 5.3 การเข้าสู่ระบบและเซสชัน

เมื่อข้อมูลถูกต้อง ฐานข้อมูลสร้าง token แบบสุ่ม ส่งกลับให้ Next.js และ Next.js เก็บในคุกกี้ `HttpOnly` อายุไม่เกินเจ็ดวัน เบราว์เซอร์ JavaScript อ่าน token นี้ไม่ได้ ในฐานข้อมูลเก็บเฉพาะค่า SHA-256 hash ของ token

หากกรอก PIN ผิดครบห้าครั้ง บัญชีจะถูกพักการลองเป็นเวลา 15 นาที และแต่ละผู้ใช้มีจำนวนเซสชันพร้อมกันจำกัด

## 6. หลักการทำงานของภารกิจ

### 6.1 ประเมินเหตุและเรียงลำดับ

ผู้เรียนเลือกและจัดลำดับการช่วยเหลือ ระบบเปรียบเทียบตำแหน่งที่เลือกกับลำดับอ้างอิง แล้วสรุปจุดผิดพลาดสำคัญก่อนรายละเอียดทั้งหมด เป้าหมายคือให้เข้าใจเหตุผลของลำดับ ไม่ใช่จำเพียงคะแนน

### 6.2 จำลองแจ้งเหตุ 1669

ระบบแสดงคำถามของเจ้าหน้าที่ทีละข้อ ผู้เรียนเลือกคำตอบที่ให้ข้อมูลครบและชัดเจน เช่น สถานที่ จำนวนผู้ป่วย อาการ และช่องทางติดต่อ หลังตอบจะได้รับ feedback ทันที การทำงานนี้เป็นแบบจำลอง ไม่ได้โทรออกจริง

### 6.3 ฝึกจังหวะ CPR

ระบบสุ่มจำนวนรอบฝึก 2–4 เซ็ต เซ็ตละ 30 ครั้ง แล้ววัดช่วงเวลาระหว่างการแตะเพื่อคำนวณ BPM เปรียบเทียบกับช่วงเป้าหมาย 100–120 ครั้งต่อนาที การคำนวณใช้ข้อมูลช่วงล่าสุดเพื่อตอบสนองต่อจังหวะปัจจุบันได้รวดเร็ว

สิ่งที่ระบบวัดได้คือจังหวะการแตะหน้าจอเท่านั้น ไม่วัดแรง ความลึก ตำแหน่งมือ การคืนตัวของหน้าอก หรือคุณภาพการช่วยหายใจ

### 6.4 AED

AED อยู่ในบทเรียนและภารกิจเสริม ผู้เรียนสามารถเลือกฝึกได้โดยไม่ถูกใช้เป็นเงื่อนไขปลดล็อกภารกิจหลัก เนื้อหาจำลองการทำตามคำสั่งเครื่อง การติดแผ่น การหลีกเลี่ยงการสัมผัสผู้ป่วย และกรณีเครื่องแนะนำหรือไม่แนะนำให้ช็อก

### 6.5 การสรุปผล

เมื่อจบภารกิจ ระบบรวมผลด้านลำดับ การแจ้งเหตุ และจังหวะ CPR พร้อมแสดงหัวข้อที่ควรทบทวน หากเข้าสู่ระบบ ระบบจะสร้าง attempt ID เพื่อป้องกันการส่งผลซ้ำ ตรวจช่วงคะแนน เวลา และอัตราการส่ง ก่อนบันทึกผล

## 7. XP และอันดับผู้ฝึก

XP คำนวณจากการทำภารกิจและโบนัสตามผลที่ทำได้ อันดับแสดงคะแนนฝึกที่ดีที่สุดตามสูตรปัจจุบัน โดยไม่เปิดเบอร์โทรหรือข้อมูลส่วนตัวต่อสาธารณะ ฐานข้อมูลจำกัดสถานการณ์ที่ยอมรับ ช่วงคะแนน เวลาขั้นต่ำ การส่งซ้ำ และจำนวนผลต่อวัน

เนื่องจากคะแนนพื้นฐานคำนวณจากเบราว์เซอร์ ผู้ใช้ที่ตั้งใจแก้ไขคำขออาจสร้างคะแนนที่ดูเป็นไปได้ ดังนั้นระบบนี้ต้องคงสถานะเป็น gamification เท่านั้น

## 8. แบบประเมินหลังใช้งาน

แบบประเมินเปิดสำหรับผู้ที่เข้าสู่ระบบและเรียนหรือฝึกตามเงื่อนไขที่กำหนด ผู้ใช้ให้คะแนนความพึงพอใจ ประโยชน์ของความรู้ และความคิดเห็นเพิ่มเติม ผู้ใช้หนึ่งคนสามารถแก้ไขคำตอบของตนเองได้ ข้อมูลดิบไม่แสดงในหน้าเว็บสาธารณะและดูได้จากหลังบ้านเท่านั้น

## 9. หลักการทำงานของหลังบ้าน

ระบบมีบัญชีผู้ดูแลจริงเพียงหนึ่งบัญชี ผู้ดูแลเข้าสู่ระบบด้วยช่องทางเดียวกับผู้ใช้ปกติ แล้วเปิด `/admin` ในเบราว์เซอร์เดียวกัน

คำขอหลังบ้านต้องผ่านสองเงื่อนไขพร้อมกัน:

1. คุกกี้เซสชันต้องเป็นของผู้ใช้ที่ตรงกับบัญชีผู้ดูแลใน `admin_config`
2. เซิร์ฟเวอร์ต้องส่ง `NONG_PROM_ADMIN_SECRET` ซึ่งเก็บเป็น Secret ใน Vercel และตรวจเทียบ hash ใน Supabase

หลังบ้านแบ่งข้อมูลเป็น:

- ผู้ใช้งาน: ชื่อ เบอร์แบบปิดบางส่วน โรงเรียน ชั้นปี คะแนนสูงสุด และกิจกรรมล่าสุด
- ผลการฝึก: จำนวนครั้ง คะแนนรวม และข้อมูลจังหวะ CPR
- แบบประเมิน: คะแนนและข้อคิดเห็นของผู้ใช้
- การเข้าสู่ระบบ: จำนวนเซสชันและเวลาที่ใช้งานล่าสุด

การลบผู้ใช้เป็นการลบถาวร ผู้ดูแลต้องพิมพ์ชื่อที่แสดงให้ตรง ระบบห้ามลบบัญชีผู้ดูแล ลบข้อมูลที่สัมพันธ์กันตาม cascade และบันทึกเหตุการณ์ใน audit log โดยไม่เก็บข้อมูลส่วนบุคคลของผู้ถูกลบไว้ใน log

## 10. การไหลของข้อมูลสำคัญ

### การเข้าสู่ระบบ

```text
เบอร์โทร + PIN
  → POST /api/player/auth
  → ตรวจ origin รูปแบบ และความยาว
  → Supabase ตรวจ hash/lockout
  → สร้าง session token
  → Next.js ตั้ง HttpOnly cookie
  → ส่งเฉพาะข้อมูลโปรไฟล์กลับหน้าเว็บ
```

### การบันทึกผลฝึก

```text
ผลภารกิจในเบราว์เซอร์
  → POST /api/player/attempt
  → ผูกกับผู้ใช้จาก session cookie
  → ตรวจ schema และช่วงข้อมูล
  → Supabase ตรวจ replay/rate/daily limits
  → บันทึก attempt
  → คำนวณข้อมูลโปรไฟล์และอันดับใหม่
```

### การอ่านข้อมูลหลังบ้าน

```text
หน้า /admin
  → GET /api/player/admin/overview
  → ตรวจ session ผู้ดูแล
  → แนบ server-only secret
  → Supabase ตรวจ admin_config และ secret hash
  → คืนข้อมูลแบบ private, no-store
  → แสดงตารางและรายละเอียดใน Dashboard
```

## 11. หลักการรักษาความปลอดภัย

| ชั้น | มาตรการ |
|---|---|
| หน้าเว็บ | React escape ข้อความ ไม่มี raw HTML หรือ dynamic code execution |
| การส่งข้อมูล | ใช้ HTTPS ตรวจ same-origin และรับ mutation แบบ JSON |
| เซสชัน | HttpOnly, Secure ใน Production, SameSite Strict และจำกัด path |
| API | ตรวจชนิด ความยาว ช่วงค่า UUID และส่งข้อความผิดพลาดแบบไม่เปิดรายละเอียดภายใน |
| Cache | ข้อมูลส่วนตัวและหลังบ้านใช้ `private, no-store` |
| ฐานข้อมูล | เปิด RLS ปิด direct grants และเปิดเฉพาะ RPC ที่กำหนด |
| PIN | hash ด้วย bcrypt มี lockout หลังกรอกผิดซ้ำ |
| ผู้ดูแล | ใช้ทั้ง player session และ server-only secret |
| การลบ | ยืนยันชื่อ ห้าม self-delete และสร้าง audit record |
| เว็บเซิร์ฟเวอร์ | CSP, HSTS, frame denial, MIME protection และ permissions policy |

Publishable key ของ Supabase ถูกออกแบบให้ใช้ใน client configuration ได้ แต่ไม่ได้ให้สิทธิ์อ่านตารางโดยตรง ส่วน database password, service-role key และ admin secret ห้ามส่งไปที่เบราว์เซอร์หรือบันทึกใน Git

## 12. โครงสร้างโค้ด

| ตำแหน่ง | ความรับผิดชอบ |
|---|---|
| `src/app/` | หน้าเว็บ Layout CSS และ API Route Handlers |
| `src/components/` | UI ส่วนกลาง โปรไฟล์ แบบประเมิน และ Dashboard |
| `src/features/` | ประสบการณ์แต่ละบทเรียนและภารกิจ |
| `src/data/` | เนื้อหาบทเรียน สถานการณ์ และแหล่งอ้างอิง |
| `src/lib/` | การคำนวณคะแนน เซสชัน client/server และการเชื่อมฐานข้อมูล |
| `src/lib/__tests__/` | unit/component/security-contract tests |
| `supabase/migrations/` | schema, function, permission และประวัติการเปลี่ยนฐานข้อมูล |
| `docs/` | แผน UX รายงาน และคู่มือดูแลระบบ |

หลักการแก้ไขคือ UI ไม่ควรติดต่อฐานข้อมูลโดยตรง การเปลี่ยน schema ต้องสร้าง migration ใหม่ และ business rule สำคัญต้องมีการตรวจทั้งที่ API และฐานข้อมูล

## 14. ข้อจำกัดและความเสี่ยงคงเหลือ

1. ยังไม่มี rate limiting ระดับ IP แบบถาวรสำหรับการสมัครและเข้าสู่ระบบ
2. เบอร์โทรไม่ได้ยืนยันด้วย OTP จึงไม่ใช่หลักฐานยืนยันเจ้าของเบอร์
3. ยังไม่มีระบบกู้ PIN อัตโนมัติ
4. คะแนนฝึกมาจากเหตุการณ์ใน client จึงไม่เหมาะกับผลสอบหรือการรับรอง
5. ยังต้องกำหนดอายุการเก็บโปรไฟล์ ผล และแบบประเมินอย่างเป็นทางการ
6. ต้องทดสอบการใช้งานจริงบน iPhone, Android และ iPad ก่อนใช้งานวงกว้าง
7. การลบผู้ใช้เป็นการลบถาวรและไม่มีปุ่มกู้คืนในหลังบ้าน

## 15. ข้อเสนอแนะในการพัฒนาระยะถัดไป

ลำดับเร่งด่วนที่แนะนำ:

1. เพิ่ม rate limiting ที่ Vercel Firewall หรือชั้น edge สำหรับ `/api/player/auth`
2. กำหนดนโยบายเก็บและลบข้อมูล พร้อมงาน cleanup ตามกำหนด
3. จัดทำขั้นตอนเปลี่ยน PIN ผู้ดูแลและหมุน admin secret ที่มีผู้รับผิดชอบชัดเจน
4. เพิ่ม integration/E2E test สำหรับ Guest, ผู้ใช้ปกติ และผู้ดูแล
5. ทำ staged load test ที่มีทั้ง login อ่าน leaderboard ส่งผล และอ่านหลังบ้าน
6. เพิ่ม export แบบไม่เปิดข้อมูลเกินจำเป็น หากครูฝึกต้องสรุปผลเป็นรายรุ่น

## 16. สรุป

น้องพร้อมใช้แนวคิด “เปิดให้เรียนง่าย แต่แยกขอบเขตข้อมูลชัดเจน” ผู้เรียนไม่ต้องเข้าสู่ระบบเพื่อเริ่มฝึก ขณะที่ข้อมูลถาวรและความสามารถหลังบ้านต้องผ่านเซสชันและการตรวจสิทธิ์หลายชั้น โครงสร้างปัจจุบันรองรับการทดลองใช้แบบมีผู้ดูแลได้ดี และมีหลักฐานจาก tests, build, dependency audit และ production smoke test

ก่อนนำไปใช้เป็นระบบประเมินอย่างเป็นทางการ ต้องแก้ข้อจำกัดด้านการพิสูจน์ตัวตน ความน่าเชื่อถือของคะแนน การเก็บรักษาข้อมูล และการตรวจทักษะภาคปฏิบัติให้ครบก่อน
